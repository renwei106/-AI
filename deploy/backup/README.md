## 本次范围及已核实的保存链路

- `dist/account-access.js` 的 `saveAccountData()` 将完整空间树 PUT 到 `/api/shiyu/auth/account`。
- 关联后台 `shiyu-user-plugin.ts` 将空间树保存为用户的 `accountData`，工具接口将小记、待办、收藏卡片保存为 `toolData`；它们位于同一个 `SHIYU_USERS_FILE` 指定的 JSON 文件，默认 `.local/shiyu-users.json`。
- 小记、待办、收藏工具具有 revision 检查。空间树当前没有相同的乐观锁机制；两个窗口提交旧状态可能互相覆盖。快照忠实保留服务端收到的结果，不会自动修复同步冲突。
- 原文件同时含账号及其他字段，工具完整加密保留原字节，不删除未知字段、不按网址去重、不重排数组、不改 ID、不筛掉归档/垃圾桶内容。
- 服务端以临时文件 rename 发布账号 JSON。工具读取一次已打开的文件描述符，取得该文件版本，检查读取期间大小及时间戳；并非分别导出各用户/各模块后拼接。上线前仍需确认生产实际写入方式及所有写入者。
- 前端本地偏好、尚未提交的草稿、离线修改、尚未迁移到 toolData 的历史本机数据不在本快照内。必须明确区分“本机保存”“服务端保存”“异地备份成功”。

## 新数据和历史数据的行为

每次执行都从源文件重新读取完整最新状态，并生成独立时间戳及随机 ID 的快照：

1. 新建网址、空间、场景、分组：新快照包含新条目。
2. 修改标题、内容、网址：新快照包含新值，旧快照保留旧值。
3. 移动和排序：新快照保留新父子关系及数组顺序。
4. 删除：新快照不包含已删除条目；保留期内的旧快照仍有删除前状态。

这不是每次点击的审计日志；两个备份点之间新增又删除的条目可能不在任何快照里。网址目前是数组条目，不能把快照对比宣称为具有稳定网址 ID 的逐操作追溯。快照也不是空间树和收藏引用两次 HTTP 请求的跨请求事务：捕获到中间状态时会报告可发现的引用问题，但不声称检查覆盖全部业务不变量。

## 工具能力

- AES-256-GCM 加密及完整性认证，随机 nonce；内部保存 SHA-256 原文校验和。
- 生成后先内存解密校验，再读回落盘文件验证。
- 快照写入、fsync 后以不覆盖的方式发布；中断留下的 `.partial` 文件不是成功快照。
- 检查用户/空间/场景/分组 ID、工具版本、主要集合结构、收藏引用、部分小记排序引用。已有悬空引用只报告、不自动改业务数据。
- 恢复要求指定预期环境，并只输出到全新的隔离目录，拒绝覆盖现有目录或在线数据。
- 只处理账号 JSON，**不包括**订单 SQLite、邀请独立文件、全站配置、权限中心、分享/反馈文件、上传资源、证书等。会员字段在账号文件里不意味着订单账本也已备份；严禁直接用此工具的全库输出覆盖生产账号库而跳过支付对账。
- 不创建计划任务、不自动上传、不删除历史、不修改前后台运行代码。
- 单个源文件上限 256 MiB，压缩/加密在内存执行；超过后应升级为流式方案，不能静默截断。Windows 权限由部署者配置 ACL，POSIX 密钥要求 0600 或更严格。

## 本地验证

运行 `node --test deploy/backup/account-snapshot.test.cjs`。全部使用临时构造的测试账号，不读取真实账号文件。场景包括新增、修改、移动、排序、删除、多用户隔离、同网址不同位置、异常引用、密钥错误、数据篡改、环境误用及拒绝覆盖。每个历史版本恢复后与当时源文件逐字节对比。

以下路径为占位示例，不能直接当作生产配置执行；密钥父目录、恢复目标父目录须事先存在。运行 Node.js 24。

```text
node deploy/backup/account-snapshot.cjs keygen --key-file <独立安全目录/key.bin>
node deploy/backup/account-snapshot.cjs create --source <账号JSON真实路径> --vault <备份目录> --key-file <独立安全目录/key.bin> --environment test
node deploy/backup/account-snapshot.cjs verify --file <某个.shiyubak> --key-file <独立安全目录/key.bin> --environment test
node deploy/backup/account-snapshot.cjs restore --file <某个.shiyubak> --target <尚不存在的隔离目录> --key-file <独立安全目录/key.bin> --environment test
```

退出码：0=本地快照及结构检查通过；1=操作失败；2=已保存原文快照，但发现需审查的关系警告。CLI 不输出账号内容或密钥。`offsiteVerified: false` 明确表示本地成功不等于异地成功。

## 拟上线计划（尚未启用）

- 同一账号 JSON 中包含核心账号及会员字段，拟整体每 15 分钟一次；它包含的用户内容随之获得更高频率保护。其他独立用户文件每小时、配置/分享/反馈/统计每天，重要变更前另做快照。
- 高频版本保留 48 小时，每日版本 30 天，每月版本 6 个月。此版没有自动清理代码；待异地校验、保留策略测试完成后才开启清理。
- 第一阶段先写本机独立备份目录。用户提供硬盘后复制快照与独立保管的密钥，执行下载/复制后的恢复演练；后续再按用户选择接入另一台服务器或独立对象存储。异机凭据不得有删除历史副本的权限。
- 只有来源采集、加密、远端上传、远端下载校验全部完成，才更新“最近异地成功时间”。失败、长时间无成功副本、关系警告都应通知。不得把进程退出 0 作为完整异地备份成功。
- 用数据清单补齐 SQLite 和其他业务文件，并设计订单/会员的协调捕获或恢复对账。不能把跨文件逐个拷贝称为同一事务时间点。
- 首次启用前在隔离环境恢复，再通过应用验证账号空间、收藏、小记、待办、订单及权益。每月演练；目前只有数据层自动测试，尚无生产数据或真实页面恢复验收。

## 异常记录和后台手动恢复

`run-backup.cjs <配置文件绝对路径>` 为每次任务记录 started / finished 两份不可覆盖的 JSON。内容包括开始/结束时间、失败环节、脱敏原因、快照路径、校验值、数据数量、工具覆盖统计和关系警告。磁盘满、权限不足、来源不存在、结构校验失败等可区分；来源损坏的异常文本不会直接写入日志，以免泄露用户数据。若日志本身写不进去，则在 systemd journal 输出错误并失败退出。只有 started 没有 finished 的任务应视为中断，不能视为成功。

任务安装后可用 `journalctl -u shiyu-account-backup.service` 查看系统执行日志；目前任务尚未安装。此版没有主动通知渠道，也没有后台页面，不能声称用户已经能在后台看到。
