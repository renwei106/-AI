# 会员活动中心

本地开发版本，未上线。后台入口为 `/apps/shiyu/activities`，参与明细为
`/apps/shiyu/activity-records`，异常与操作记录为 `/apps/shiyu/activity-audit`。
邀请奖励及奖励明细菜单归入活动中心，原访问路径、邀请数据和计奖逻辑保持不变。

## 生效规则

- 可选全部用户或活动期间新注册用户；未配置范围的历史活动按全部用户处理。新用户注册时间从原用户库读取，需在活动区间内且不晚于当前时间；无注册来源、渠道门槛。
- 价格设置分为统一折扣、按套餐折扣、按套餐活动价、正常售价。赠天独立开启并按套餐填写；关闭后忽略残留赠天值。正常售价需搭配赠天。
- 同套餐、重叠时间允许多个活动，优先级数字越大越优先；相同优先级禁止启用。
- 符合用户参与范围的活动中，仅最高优先级活动生效，不跨活动叠加。额度耗尽后按正常价购买，不顺延其他活动。
- 活动总份数、套餐总份数、账号累计份数、账号套餐份数同时校验。超额部分正常价且不赠天。
- 活动启用后锁定规则；修改需复制为新活动。草稿修改使用版本校验，防止覆盖其他管理员保存。
- 活动时间是北京时间，起点包含、终点不包含。优惠订单支付期限为创建后 10 分钟与活动结束时间的较早者。
- 停用阻止新参与，已创建订单在原期限内有效；规则版本和订单价格不会被追改。
- 折扣按下单时正常销售价计算，精确到分；固定价不可超过正常价；负数始终禁止。
- 输入 0 元活动价或折扣计算后为 0 元时自动按零元领取处理；留空和负数不允许。同样创建正式订单，渠道记为 `free`，内部完成领取，不调用微信/支付宝。
- 活动结束不影响已购买会员时长。赠天计入原订单时长与到账事件，单独记录活动赠送份额。

## 数据边界

复用支付配置中的 `database` 文件，活动表和订单表同库事务，避免跨库预占不一致。

| 数据 | 存储与用途 |
| --- | --- |
| 用户、会员状态 | 原用户存储和会员服务，活动中心不复制用户资料 |
| 订单、支付、套餐快照 | 原 `orders`、`ledger` 等表，不创建活动专属订单库 |
| 活动状态 | `activities`，保存活动标识、状态、当前版本 |
| 活动规则历史 | `activity_versions`，不可变规则版本和操作人 |
| 参与事实 | `activity_participations`，订单 ID、活动及版本、优惠份数、优惠金额、赠天 |
| 操作依据 | `activity_audit`，只追加，关联活动/订单/用户 ID、操作人、原因、时间 |
| 异常队列 | `activity_issues`，异常及解决状态；处理经过在审计记录中保留 |

后台显示用户名称、订单金额、支付和到账状态时，关联原数据读取。活动版本、
实际优惠及赠天是独立业务事实，用于解释当时结算依据，不是订单或用户的重复副本。

## 并发、恢复与纠错

报价接口 `/api/shiyu/payments/quote` 返回服务端计算结果及确认标识。下单在
`BEGIN IMMEDIATE` 事务内重新报价，校验已确认内容、限购、名额并创建订单和参与关系。
价格/资格发生变化时返回 `QUOTE_CHANGED`，前端刷新后要求用户再次确认，不静默加价。
请求 ID 负责订单幂等；到账事件 `PAY:<orderId>` 负责会员发放幂等。

支付超时不直接释放名额。任务先查询渠道，确认已付则按真实付款时间处理；未付则关单，
只有渠道确认关单才释放。网络不明、查单/关单失败继续保留名额并记录异常，后续重试。
已在期限内支付但通知延迟的正常到账；超期支付或已释放名额后收到付款进入人工核查，
不自动发放。用户可查询付款已收到及需要核查的状态。

后台可重试会员到账、核查付款、确认异常订单补发、追加备注。人工操作必须填写原因，
记录操作人；重复补发不会重复延长同一订单的权益。这里没有直接改订单金额、删除账本或
自动退款入口。退款仍由既有人工流程核查，活动额度不会因备注自动恢复。

邀请逻辑默认排除这些优惠订单；开启“本活动购买可触发邀请奖励”后才按原邀请规则评估。
零元始终不算付费。排除订单不会消耗后续首次合格付费机会；历史已发放奖励不追溯修改。

## 本地验证与发布边界

验证命令（导航站目录）：

```powershell
node --test payments/test/*.test.cjs
node checks/activity-center-ui.cjs
node checks/activity-member-ui.cjs
```

页面测试的活动/用户/订单使用内存或临时存储，不创建线上活动、不发起真实收款。
截图位于 `checks/activity-center/`。后台构建在聚合管理后台执行 `tsc -b` 和 `vite build`。

发布需同时包含活动后台插件、支付服务及会员购买脚本，并确认后台与支付进程使用同一
支付数据库、用户路径、邀请路径和环境。后台接口沿用现有拾隅权限校验及同源写入限制；
现有 Vite 开发 Mock 登录不代表生产认证能力。

旧订单库 `amount>0` 的约束需迁移为 `amount>=0`；迁移保留既有数据、索引、触发器及外键。
发布前需备份数据库及会员数据，停止旧写入进程，先在副本验证迁移，再启动同版服务；
产生零元订单后不可简单回退到不认识 `free` 渠道的旧服务。

真实渠道的支付截止、关闭订单和回调联调仍需在受控环境验证。上线前另行核对共享影响、
接口、回调、配置、版本号，取得用户明确确认，并追加上线记录。本次未执行发布。
